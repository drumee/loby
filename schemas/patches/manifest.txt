# loby onboarding: record the invite step's answer on the response row.
#
# Paths are relative to loby/schemas. APPLY ORDER MATTERS:
#   1. the additive column migration, before anything reads or writes invites;
#   2. the procedure that writes it;
#   3. get_onboarding_response, which now returns the column so a resumed
#      session can read it back.
#
# Do NOT add tables/onboarding_responses.sql here — that file begins with
# `DROP TABLE IF EXISTS` and would destroy live data. Existing instances are
# migrated with the ALTER patch below; the full table def is for fresh
# installs only.
#
# Prerequisite: instances must already be on the onboarding v2 baseline
# (alter_onboarding_responses_v2.sql), the "other" patch
# (alter_onboarding_responses_other.sql) and the identity patch
# (alter_onboarding_responses_identity.sql), whose onboarding_resolve_row
# every procedure below calls.
#
# DEPLOY TOGETHER WITH the loby service: save_onboarding_invites is reached
# through onboarding.save_invites, which ships with acl/onboarding.json.
# Applying the SQL without the service leaves the column permanently NULL;
# deploying the service without the SQL makes every invite-step save fail.
#
# The onboarding-ui client tolerates the service being absent — it warns and
# carries on rather than blocking the step — so a UI deployed ahead of this
# patch degrades to "invites are sent but not recorded" instead of breaking.
migrations/alter_onboarding_responses_invites.sql
procedures/save_onboarding_invites.sql
procedures/get_onboarding_response.sql
# Independent of the three above, and carried here because instances other than
# stage have not had it: an empty value now CLEARS intent instead of raising
# 'Invalid intent value', which is what lets the wizard's "Tell me later"
# retract a goal the user had already chosen.
procedures/save_onboarding_intent.sql
